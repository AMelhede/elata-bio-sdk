`recordPulseCheckInputs` (off by default): the session keeps what the pulse check was fed (each frame's forehead and cheek colours, the wall as tracked and as the camera read it, why no wall was found, the head, frames with no face, the SDK's own rate on the agreement path) and every `getMetrics()` read with the rate it showed and the session's own reason for showing none. `session.getPulseCheckRecording()` returns it; `serializePulseCheckRecording` and `parsePulseCheckRecording` write and read it as JSON (`format: "rppg-web/pulse-check-inputs"`, `version: 1`) with every number kept exactly; `replayPulseCheck(recording, { rules })` runs it through the same `PulseCheck` code with any rules, so every dim-light candidate can be judged on the seconds a reference sensor saw. `RecordingPulseCheck` does the same for an app that builds its own runner. A `seconds` that is not a positive number is refused (RangeError) before the session loads a face finder or an engine. `PulseCheck.evaluations` counts the check's judgements, for the replay. Tested: through the session, a replay with the session's own rules gives back every shown number and every state of the check, including reads hidden for no face or a failed engine; recording on and off give the same reads; each recorded field, taken out, turns a test red. Costs: memory, the newest 5 minutes by default and at most 120 events a second of that (measured at 30 frames a second with one read per frame: 18,000 events, about 7 MB held, 3.6 MB as JSON); no measurable time per frame. A recording that let its start go (`dropped` above 0) replays as a check that began at its first kept event, so its first numbers can differ from what was shown. A saved file holds the skin's colour over time, from which a pulse can be read: it is the person's data.
